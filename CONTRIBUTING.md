# Contributing to attestation

Thank you for your interest in contributing to `attestation`! This document describes how to set up the project, which checks a change must pass, and how releases are made.

## Development Setup

### Prerequisites

- Node.js `^20.19.0 || >=22.12.0` (CI uses Node.js 24)
- npm (the repository is an npm workspace locked with `package-lock.json`)
- A C++ toolchain for the native `pkcs11js` module that `graphene-pk11` (Yubico) uses; `npm ci` builds it

### Installation

```bash
git clone https://github.com/PeculiarVentures/attestation.git
cd attestation
npm ci
npm test
npm run build
```

## Project Layout

- `packages/common/` is `@peculiar/attestation-common`: the shared `AttestationProvider` interface and result types.
- `packages/marvell/` is `@peculiar/attestation-marvell`: the Marvell evidence parser, the generic and Google Cloud HSM verification profiles and the bundled roots. `packages/marvell/test/fixtures.ts` holds evidence and certificate fixtures shared by its specs.
- `packages/yubico/` is `@peculiar/attestation-yubico`: the PIV attestation provider, the bundled Yubico roots and intermediates, and the PKCS#11 token manager.
- `packages/cli/` is `@peculiar/attestation-cli`, the `attest` command. It is an application: `src/main.ts` is built to `bin/main.js`, and it has no library entry.
- `packages/<name>/src/index.ts` is a library's only public entry point and must stay aligned with its `exports`.
- `tsdown.config.ts` at the repository root builds every package (tsdown `workspace` mode): the three libraries with declarations, the CLI as one executable. There are no per-package build configs.
- `tsconfig.json` at the root is used for typechecking, tests and the declaration build. Its `paths` map every `@peculiar/attestation-*` package to its `src`, so packages and tests use the sibling sources without building them first.
- `packages/<name>/build/` and `packages/cli/bin/` are generated by `npm run build` and are not committed.

## Development Workflow

### Code Quality

Before opening a pull request, run from the repository root:

```bash
npm run lint          # oxlint
npm run format:check  # oxfmt
npm run typecheck     # tsc --noEmit
npm test              # vitest, runs once and exits
npm run build         # tsdown, also checks every library with attw
```

Fix lint and formatting issues with `npm run lint:fix` and `npm run format`. Use `npm run coverage` to produce a coverage report, `npx vitest run packages/<name>` to run one package's tests, and `npm run cli -- <command>` to run the CLI from source.

### Testing

- Use Vitest: import `describe`, `it` and `expect` from `vitest` (globals are off) and assert with `expect`. `vitest.setup.ts` loads the Reflect polyfill that `@peculiar/x509` needs.
- Put tests next to the code they cover as `*.spec.ts` in `packages/<name>/src/`.
- Cover new behavior and bug fixes with tests. For parsing or verification changes, build real evidence or certificates and check the exact results, including the failure reasons.
- Keep tests deterministic: no wall-clock time, network access, external services or hardware tokens.

### Build And Package Exports

Every library is ESM-only; there is no CommonJS build, and CommonJS consumers load it through `require(esm)`. tsdown builds `src/index.ts` into `build/index.js` with `.d.ts` declarations. Output is unbundled, so every source module is emitted under `build/` mirroring `src/`, but only the root entry is reachable through `exports`. The syntax target comes from `engines.node`; do not set `target` in `tsdown.config.ts`.

`exports` and the legacy `main`/`module`/`types` fields in each library's `package.json` are generated by tsdown on every build and must not be edited by hand. CI fails if the build changes a `package.json`.

Use named exports only (no `export default`) and no top-level `await`, so `require()` of the libraries keeps working on supported Node.js versions. Use `import type` for type-only imports (`verbatimModuleSyntax`); `import { type X }` still leaves a side-effect import of the module in the output.

TypeScript 7 has no compiler API, so tsdown generates the declarations with Oxc (`dts.generator: "oxc"`). Code must follow the `isolatedDeclarations` rules: exported functions, constants and class members need explicit types, or the build fails.

The three libraries have `"sideEffects": false`. Nothing registers state at import time: Marvell resolves x509's algorithm provider from the tsyringe container when it runs. Don't add code that only works because a module was imported for its side effects; the CLI is the exception and is not marked.

### Dependencies

- `@peculiar/x509` is a **peer** dependency (and a dev dependency) of every library, and `@peculiar/asn1-schema` and `tsyringe` are peers of `-marvell`: the APIs take and return x509 objects, and Marvell resolves from the tsyringe container that x509 registers into, so an app must have only one copy of each.
- `@peculiar/asn1-*` schema packages, `@peculiar/utils`, `pako` and `graphene-pk11` are regular `dependencies`. Use the `@peculiar/utils` root or subpath entries, never `/legacy`.
- `@peculiar/attestation-common` is a regular dependency of the providers. Internal `@peculiar/attestation-*` ranges are bumped by the release pull request; don't change them by hand.
- The CLI is an application and keeps everything in `dependencies`.

### Commit Messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Pull requests are squash-merged, so the pull request title becomes the commit message and must follow the same format.

```plain
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`. Use the package directory as the scope for package-specific changes (for example `fix(marvell): ...`, `feat(cli): ...`).

Mark breaking changes with `!` after the type or scope (for example `feat(marvell)!: ...`) and/or a `BREAKING CHANGE:` footer.

### Pull Requests

1. Fork the repository and create a branch from `main`.
2. Make your changes, with tests.
3. Run the checks listed above.
4. Open a pull request with a Conventional Commit title.

## Code Style

- Write TypeScript.
- Follow the oxlint (`.oxlintrc.json`) and oxfmt (`.oxfmtrc.json`) configuration. Prefer fixing the source over adding rules, and disable a rule inline only with a reason (`// eslint-disable-next-line <rule> -- <reason>`).
- Keep changes small and localized to the owning package.
- Prefer `BufferSource`-based public APIs over Node.js-specific `Buffer` types in the libraries.
- Keep public exports stable; breaking changes need a major release.

## Releases

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`) and the **Release** workflow (`.github/workflows/publish.yml`). The four packages share one version, one `v<version>` tag and one GitHub Release; the private root package carries the version.

1. On every push to `main`, the Release workflow first runs the **Test** workflow (`test.yml`). Only when it passes does release-please open or update a `chore(release): vX.Y.Z` pull request. It bumps the root and every `packages/*/package.json` version, the internal `@peculiar/attestation-*` ranges, and `package-lock.json`. The version comes from the commits: a breaking change bumps major, `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types do not trigger a release. Any releasable commit releases every package.
2. Review the release pull request: the four versions, the internal ranges, the lockfile and the notes. Don't edit the generated versions by hand.
3. Merge it. release-please creates the `vX.Y.Z` tag and the GitHub Release with the notes from the pull request. The publish job then checks that the release commit is the one being built, runs `npm ci --ignore-scripts` and the build, checks that the generated exports are committed, checks that every package has the release version, and publishes dependencies first (`common`, then `marvell` and `yubico`, then `cli`) via Trusted Publisher with provenance, skipping versions already on npm. Finally the major tag (for example `v3`) moves when this is the newest release of that major.

Lifecycle scripts never run in the publish job, so the release build must not need dependency install scripts.

Release notes live only in [GitHub Releases](https://github.com/PeculiarVentures/attestation/releases); there is no `CHANGELOG.md`. Only `feat`, `fix`, `perf`, `build`, `revert`, and breaking changes are listed. Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description before the release pull request is merged; edits to the release pull request description are overwritten when new commits land.

### Retrying A Publish

Open **Actions → Release → Run workflow** and select the existing `vX.Y.Z` tag. Branches and tags that don't match the package version are rejected; don't rerun from `main`, change versions or move the tag. The retry builds the tagged source, skips versions already on npm and stops at the first failure, so run it again once access or the registry is fixed, then check all four npm versions.

Retry a partial release before making a newer one: `npm publish` tags what it publishes as `latest`, so retrying an older version after a newer one shipped would move `latest` backwards. Publish such a version by hand with a maintenance dist-tag instead.

### One-Time Setup

- **npm Trusted Publisher** for each of `@peculiar/attestation-common`, `-marvell`, `-yubico` and `-cli`: organization `PeculiarVentures`, repository `attestation`, workflow `publish.yml`, environment `npm`. A new package must be published once by a maintainer before it can be configured. No npm token is used. See the [npm documentation](https://docs.npmjs.com/trusted-publishers/).
- **GitHub environment `npm`:** allow deployments from `main` and from `v*` tags (for retries); add protection rules if you want a manual gate.
- **`RELEASE_TOKEN` (optional):** a GitHub App token or fine-grained PAT that can open pull requests. Without it, the release pull request is opened with `GITHUB_TOKEN`, and its Test runs need a maintainer to approve them.
